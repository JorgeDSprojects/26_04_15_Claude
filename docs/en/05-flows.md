# 05 — End-to-End Data Flows

## F1 — Informative telemetry publication

**Path:** simulator → mqtt-broker

```
simulator reads CSV row (or generates synthetic value)
  → constructs topic from asset path + "measure" + signal name
  → looks up criticality from its local config cache
  → publishes to EMQX:
      topic:   aeronorth/windfarm_north/sector_a/turbine_03/rotor/measure/rpm
      payload: {"val": 14.2, "ts": 1705400100500, "q": 1}
      QoS:     0 (standard/buffered) or 1 (critical)
      retain:  false
```

**Frequency:** configurable, default 10 seconds per signal.

**Report by Exception:** the simulator may skip publishing if the value
hasn't changed since the last publish (configurable behavior).

## F2 — Historical persistence

**Path:** mqtt-broker → telegraf → TimescaleDB + Redis

```
Telegraf (mqtt_consumer input):
  subscribes to: +/+/+/+/+/measure/#
  parses JSON payload: val, ts, q
  parses topic into tags: enterprise, site, area, line, cell, signal

Telegraf (postgresql output):
  writes to TimescaleDB:
    INSERT INTO metrics (time, topic, value, quality)
    VALUES (to_timestamp(ts/1000), '<full_topic>', val, q)

Telegraf (redis output, in parallel):
  writes to Redis:
    SET lkv:<full_topic> <payload_json>
```

**Telegraf topic parsing config (conceptual):**

```toml
[[inputs.mqtt_consumer]]
  servers = ["tcp://mqtt-broker:1883"]
  topics = ["+/+/+/+/+/measure/#"]
  data_format = "json"
  json_query = ""
  tag_keys = []

  [inputs.mqtt_consumer.topic_parsing]
    topic = "+/+/+/+/+/measure/+"
    tags = "enterprise/site/area/line/cell/_/signal"
    # "_" discards the "measure" segment

[[outputs.postgresql]]
  connection = "postgres://telegraf:pass@timescaledb:5433/metrics"

[[outputs.redis]]
  address = "redis://redis:6379"
  key = "lkv:{{ .Topic }}"
  data_format = "json"
```

## F3 — Real-time distribution to frontend

**Path:** mqtt-broker → realtime-service → WebSocket → browser

```
realtime-service:
  on startup:
    → loads all signal metadata (topic→criticality map) from api-service
       via GET /api/v1/signals?enabled=true
    → subscribes to MQTT broker for topics of interest

  on MQTT message received (topic, payload):
    → updates Redis LKV: SET lkv:<topic> <payload>
    → if criticality is buffered or critical:
        XADD stream:<topic> * payload <payload>
    → for each WebSocket client subscribed to this topic:
        if criticality is standard:
          enqueue in client's asyncio.Queue (drop oldest if full)
        else:
          notify client reader coroutine that new data is available

  WebSocket client reader coroutine:
    if signal is standard:
      loop: dequeue from asyncio.Queue → send to WS
    if signal is buffered/critical:
      loop: XREAD from stream:<topic> with client's last ID → send to WS
            update client's last ID in ws:session:<client_id>
```

## F4 — WebSocket client reconnection

**Path:** browser reconnects → realtime-service → Redis → browser

```
Browser detects WS disconnect
  → waits (exponential backoff)
  → opens new WS connection to realtime-service
  → sends: {"action": "subscribe", "topics": ["...topic1...", "...topic2..."]}

realtime-service on new subscription:
  for each topic:
    1. Send LKV immediately:
       GET lkv:<topic> from Redis → send to WS
    2. If signal is buffered/critical:
       Look up last stream ID for this client from ws:session:<client_id>
       If found:
         XREAD stream:<topic> from last_id → send all missed messages
       Else:
         Start from latest (no catch-up on first connection)
    3. Resume live streaming
```

**Key detail:** the client ID is generated by the browser (e.g., UUID
stored in sessionStorage) and sent in the initial WS handshake. This
allows the realtime-service to track the client across reconnections
within the same browser session.

## F5 — Widget initial load

**Path:** browser → api-service → postgres/redis → browser

```
User opens dashboard
  → frontend: GET /api/v1/dashboards/{id} → receives layout + widget configs
  → for each widget:
      extract signal_ids from widget config
      GET /api/v1/signals?ids=1,2,3 → receives signal metadata (topic, unit, etc.)
      subscribe to topics via WS: {"action": "subscribe", "topics": [...]}

realtime-service on subscribe:
  → GET lkv:<topic> from Redis → send immediately
  → widget renders with the current value, no blank screen

If widget is a historical chart:
  → frontend: GET /api/v1/timeseries?signal_id=1&from=...&to=...
  → api-service queries TimescaleDB → returns JSON array of {time, value}
  → widget renders historical chart
  → then overlays live data from WS on top
```

## F6 — Signal registration from frontend

**Path:** browser → api-service → postgres → sync-service → mqtt-broker

```
1. Admin navigates to Signal Management in frontend
2. Clicks "New Signal", fills form:
   - Asset: selects from tree (e.g., turbine_03/rotor)
   - Name: rpm
   - Type: informative
   - Unit: rpm
   - Datatype: float
   - Criticality: buffered
   - Protocol: simulated
   - Enabled: true

3. Frontend: POST /api/v1/signals
   Body: {
     "asset_id": 15,
     "signal_type_id": 1,
     "name": "rpm",
     "display_name": "Rotor RPM",
     "unit": "rpm",
     "datatype": "float",
     "criticality": "buffered",
     "protocol": "simulated",
     "enabled": true,
     "min_value": 0,
     "max_value": 25
   }

4. api-service:
   a. Validates with Pydantic
   b. Looks up asset to get its path
   c. Computes topic: "aeronorth/windfarm_north/sector_a/turbine_03/rotor/measure/rpm"
   d. INSERT INTO signals (...) VALUES (...)
   e. Postgres trigger fires: NOTIFY signals_changed, '{"op":"INSERT","id":42}'
   f. Returns 201 Created with full signal object

5. sync-service (listening on signals_changed):
   a. Receives notification: {"op": "INSERT", "id": 42}
   b. GET signal by id from Postgres (direct SQL, same DB)
   c. Builds $meta payload from signal + asset data
   d. Publishes to MQTT:
      topic:   aeronorth/windfarm_north/sector_a/turbine_03/rotor/$meta/rpm
      payload: {"signal_id": 42, "name": "rpm", "unit": "rpm", ...}
      QoS:     1
      retain:  true

6. EMQX stores the retained message.

7. All subscribers to +/+/+/+/+/$meta/# receive the new metadata:
   - meta-ingestor: sees it matches a registered signal → no drift
   - realtime-service: updates its in-memory criticality cache
```

## F7 — Event flow (operational)

**Path:** simulator → mqtt-broker → event-ingestor → postgres
                                  → realtime-service → browser

```
1. Simulator detects trigger condition (or admin clicks "Inject Event")
2. Simulator publishes:
   topic:   aeronorth/windfarm_north/sector_a/turbine_03/controller/events/emergency_stop
   payload: {
     "event_type": "emergency_stop",
     "severity": "critical",
     "ts": 1705400100500,
     "data": {"trigger": "manual", "wind_speed": 28.3}
   }
   QoS:     1
   retain:  false

3. event-ingestor (subscribed with QoS 1, persistent session):
   a. Receives message
   b. Resolves asset from topic path (lookup in local cache or API call)
   c. INSERT INTO events (asset_id, event_type, severity, payload, occurred_at)
      VALUES (15, 'emergency_stop', 'critical', '{"trigger":...}', to_timestamp(...))
   d. ACK to broker (QoS 1 complete)

4. realtime-service (also subscribed):
   a. Receives same message
   b. Criticality for events is always "critical" → XADD to Redis Stream
   c. Fan-out to all WS clients subscribed to this topic or to event feeds

5. Frontend alarm widget:
   a. Receives event via WS
   b. Renders alarm notification with severity badge
   c. If alarm_list widget: adds to top of list with "Unacknowledged" status

6. If event-ingestor was DOWN when event was published:
   a. EMQX queues the message (QoS 1 + persistent session)
   b. When event-ingestor comes back up, EMQX delivers all queued messages
   c. event-ingestor processes them → no data loss
```

## F8 — Metadata drift detection

**Path:** mqtt-broker → meta-ingestor → postgres

```
1. Some producer publishes a $meta message for a signal that is NOT
   in the signals table (e.g., a new sensor was added to a turbine
   but nobody registered it in the platform yet).

2. meta-ingestor receives:
   topic:   aeronorth/windfarm_north/sector_a/turbine_03/nacelle/$meta/humidity
   payload: {"name": "humidity", "unit": "%RH", ...}

3. meta-ingestor:
   a. Checks its local cache of registered topics
   b. "humidity" on this asset is NOT registered
   c. INSERT INTO meta_drift (topic, payload, status)
      VALUES ('.../$meta/humidity', '{...}', 'pending')

4. Admin sees pending drift items in the admin UI
   Options:
   - "Import": creates a new signal in the registry from the drift data
   - "Ignore": marks as ignored, won't alert again
   - "Review": marks as reviewed but takes no action yet

5. If admin clicks "Import":
   a. Frontend: POST /api/v1/signals (pre-filled from drift payload)
   b. Normal F6 flow kicks in
   c. Drift record updated to status = 'imported'
```

| F1   | Simulator timer          | simulator → broker                        | —                  |
| F2   | MQTT message (measure)   | broker → telegraf                         | TimescaleDB, Redis |
| F3   | MQTT message (any)       | broker → realtime-service → WS            | Redis              |

| F5   | Dashboard open           | frontend → api-service + realtime-service | Postgres, Redis, TimescaleDB |
| F6   | Admin creates signal     | frontend → api → PG → sync → broker      | Postgres, MQTT     |
| F7   | Event trigger            | simulator → broker → event-ingestor + RT  | Postgres, Redis    |
| F8   | Unknown $meta arrives    | broker → meta-ingestor                    | Postgres           |
